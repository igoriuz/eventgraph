Architektur-Ansätze für eventgraph

Drei Wege, die gleichen Features zu strukturieren

A

Monolithisches CLI (alles in einem Paket)

Ein einzelnes TypeScript-Paket: CLI, Graph-Engine, Viewer-Generator, MCP-Server — alles zusammen.

eventgraph/
  src/
    cli/          # init, query, impact, validate, view
    graph/        # Schema, Parser, Index, Traversal
    viewer/       # HTML-Generator
    mcp/          # MCP-Server-Adapter
    schema/       # JSON Schema + Presets
  package.json    # ein Paket, ein Build

Pros

  • Einfachster Build, einfachstes Setup
  • Kein Dependency-Management zwischen Paketen
  • Schnell zum MVP

Cons

  • MCP-User installieren auch CLI, CLI-User auch MCP
  • Schwerer zu entkoppeln wenn es wächst
  • Viewer-Dependencies (HTML-Templates) im gleichen Bundle
B

Monorepo mit Core + Thin Adapters

Core-Engine als eigenes Paket, CLI und MCP als dünne Adapter darüber. Viewer als separates Paket.

eventgraph/
  packages/
    core/         # Graph-Engine, Schema, Index, Traversal
      src/
        schema/   # JSON Schema, Presets, Validation
        graph/    # In-Memory Graph, Query, Impact
        parser/   # YAML → Graph loader
    cli/          # Thin adapter: Commander.js → core
    mcp/          # Thin adapter: MCP SDK → core
    viewer/       # HTML-Generator, Templates, Assets
  package.json    # Workspace root (npm/pnpm workspaces)

Pros

  • Core ist unabhängig testbar und wiederverwendbar
  • CLI und MCP können separat veröffentlicht werden
  • Klare Dependency-Richtung: cli → core ← mcp
  • Viewer ist optional installierbar

Cons

  • Workspace-Setup braucht mehr initiale Config
  • Etwas mehr Boilerplate für ein MVP
C

Single Package jetzt, Monorepo-ready

Startet als ein Paket (wie A), aber mit klarer interner Modulstruktur, die später ohne Breaking Changes in ein Monorepo aufgeteilt werden kann.

eventgraph/
  src/
    core/           # Graph-Engine (kein CLI/MCP-Import)
      schema.ts     # Typen, JSON Schema, Presets
      graph.ts      # In-Memory Graph
      query.ts      # Query + Impact-Analyse
      parser.ts     # YAML → Graph
      validate.ts   # Validierung
    cli/            # CLI-Adapter (importiert nur core/)
      index.ts
      commands/
    mcp/            # MCP-Adapter (importiert nur core/)
      server.ts
      tools/
    viewer/         # HTML-Generator (importiert nur core/)
      generate.ts
      templates/
  package.json      # Ein Paket, aber saubere Grenzen

  # Regel: cli/ mcp/ viewer/ importieren core/
  #         core/ importiert NICHTS aus cli/mcp/viewer/

Pros

  • MVP-Geschwindigkeit von A
  • Architektur-Sauberkeit von B
  • Aufteilung in Monorepo später ohne Refactor möglich
  • Dependency-Regel ist einfach und enforcebar (ESLint)

Cons

  • Braucht Disziplin, die Importgrenzen einzuhalten
  • Kein separates Publishing bis zur Aufteilung

Empfehlung: C

Für ein Open-Source-MVP ist die Geschwindigkeit von A mit der Struktur von B der Sweet Spot. Die Import-Regel core/ ← cli/ mcp/ viewer/ ist einfach zu enforacen und macht die spätere Aufteilung trivial.
